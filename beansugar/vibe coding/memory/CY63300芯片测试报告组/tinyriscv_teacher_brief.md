# TinyRISC-V 板级调试进展（教师汇报）

**日期：2026-09-28**

## 问题
板上 RV32 核通过 CMSIS-DAP/JTAG 可被 OpenOCD 识别，但通过串口助手发送字符后未观察到预期输出；当前还需验证 UART 与 I2C/OLED 诊断链路。

## 已取得进展
1. **JTAG 通道可用。** OpenOCD 多次识别到 TAP ID `0x1e200a6f` 和 1 个 RV32 hart，并能读取芯片内存映射寄存器。调试频率为 10 kHz。
2. **串口设备已核对。** Windows 设备管理器显示 COM6 为状态 OK 的 CH340；波特率设为 115200、8N1。用户已通过 EDA 核对 CH340 与芯片 UART 引脚通路，OLED 已接入 H2 并上电。
3. **UART 控制器在最近一次复位运行后读到启用值。** `reset run` 后等待 1 秒并 halt，`mdw 0x40003C08` 返回 `0x00000003`。复位过程中 OpenOCD 曾报告 JTAG scan chain all-zero 错误，但后续寄存器读取成功。
4. **SBA 读路径可以访问系统寄存器。** DMI/SBA 读取 `0x4002180C` 得到 `0x101`，与之前 OpenOCD `mdw` 的读数一致。
5. **引脚静态电平曾读为高。** GPIOB 输入寄存器读数 `0x2C`，当时 B.2/B.3 为高电平；这不能代替 I2C 波形或从机 ACK 测试。

## 当前仍未解决
- 串口助手在先前测试中未收到预期输出。最近一次复位后 UART_CTRL 为 3，但尚未在这个新状态下重新发送 `d` 验证固件输出。
- 通过 SBA 将系统时钟寄存器 `0x4002180C` 从 `0x101` 写为 `0x121` 后，读回仍为 `0x101`；该 I2C 时钟使能位尚未成功验证。
- 曾尝试将 UART_CTRL 写为 0 再恢复为 3，过程中读回 `0, 0`；之后 reset run 再读为 3。对 SBA 写路径的结论仍不确定。
- 一次 PC 读取为 0，CPU 是否正常执行当前测试固件还需确认。
- 此前 I2C 硬件扫描代码存在协议序列问题：没有生成 START，却设置 STOP；并且 `I2C_ADDR` 的目标地址语义与手册描述不一致，因此旧扫描结果不作为有效结论。

## 对证据的限制
本地 TinyRISC-V RTL 的 `jtag_dm.v` 对 SBCS 采取简单寄存器保存方式，没有完整更新标准定义的 SBA busy/error 状态。因此 DMI 读到 SBCS 错误位为 0，不足以证明系统总线写成功。直接 SBA 读到 `0x101` 只证明读通，不证明外设接受写入。

## 下一步测试顺序
1. **先复测 UART。** 在当前 UART_CTRL=`3` 的状态下，串口助手保持 COM6、115200、8N1，清空接收区后发送一个小写 `d`，不附加 CR/LF。现有 `i2c_diag.c` 主循环按单字符处理 `d`，该步骤应打印 SCL/SDA 电平诊断。记录是否出现固件启动菜单及 `[d]` 输出。
2. **若串口仍空，先查 CPU/UART。** 读取复位运行后的 PC 与 UART 状态，判断程序是否启动、接收是否到达、发送是否发生；暂不继续改写 I2C 寄存器。
3. **若 `d` 有输出，运行 `b` 软件位扫。** 该测试用 GPIO 开漏模拟 I2C，可绕过硬件控制器。发现 ACK 后再修正并运行硬件 I2C 测试 `c`。
4. **重测硬件 I2C 时修正事务。** 按手册确认 START 生成、目标地址编码、TX FIFO 组帧和 STOP 时序，再观察 FIFO、I2C 状态和 RAW 中断寄存器。

## 当前可向老师汇报的一句话
> JTAG 读访问和 UART 控制寄存器读取正常，最近 reset run 后 UART_CTRL 为 3；但应用串口输出尚未在复位后复测，I2C 时钟寄存器的写入也未验证成功。旧硬件 I2C 扫描序列有 START/地址语义问题，下一步先确认固件 `d` 菜单输出，再用 GPIO 位扫验证总线 ACK，最后测试修正后的硬件 I2C 事务。
