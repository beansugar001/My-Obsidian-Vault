## 总体状态

**历史上已成功烧录、执行诊断固件并读回 RAM 邮箱；当前 JTAG 尚未恢复，I²C 通信验证暂时受阻。**

### 2. 接口关系已梳理

- U5：DAPLink连接到目标板的JTAG接口。
- H10：三针跳线座。1脚为TDI，2脚为PAD0，当前JTAG连接使用1-2跳帽；3脚为另一网络NET6，具体用途未确认。
- H7：底板与绿色芯片载板之间的一组连接接口，可作为测量位置。已确认10=TDI/PAD0、13=TMS、15=TCK、16=TDO、17=GND。
- 绿色载板外部焊盘编号、蓝色底板H7针脚编号、芯片PAD编号、QFN脚号属于不同编号体系，必须分别核对。

### 3. 当前硬件问题

**先按实际插接关系定位TDO测点。** 绿色载板直接插接蓝色底板，不能混用绑定图焊点号与H7排针号。旧OL测量不支持将载板断路列为首要结论；应在H7-16实际插接的载板对应接点观察TDO，继续区分外部传输和目标输出条件。用户确认DAPLink至U5杜邦线良好，该段不再重复测量。

**TDO未观察到输出，但故障位置还没有最终确定。** 除外部连接问题外，仍可能涉及封胶内绑定、TAP工作条件或内部输出驱动。目前不能下“芯片TDO已烧坏”的定论。

**输入活动不等于有效扫描。** 尚未保存足以核对TCK/TMS/TDI完整时序的同步波形；也没有独立证明信号实际到达裸片。单独看到脉冲不能把这些项目勾为通过。

**MPU及I²C物理总线仍未完成验证。** 前期由OLED改用标有MPU-9250/6500/9255的模块；实际芯片型号、模块端供电、共地、nCS/AD0以及SCL/SDA波形均需要在恢复调试后继续确认。尚无有效ACK或身份读取结果。OLED此前未点亮，不能用它作为当前I²C好坏判断的可靠对照。

**UART物理链路未闭环。** 用户报告CH340和H4各自本地回环可用，交叉连接仍未获得有效接收/banner；尚未通过可靠波形确认TX输出、实际波特率与跨设备接收。

### 4. 已纠正的硬件误判

- 曾因错认H7针脚测到TCK为低或OL；正确H7-15随后测得0.6Ω且有活动，旧结果撤回。
- 曾把“H7-5上方焊点”当作绿色载板5号/PAD3；该测量不能作为芯片侧TMS证据。
- 最初用户报告过U5-2疑似方波，但当时接地/倍率尚未确认，出现过17.8V或超过25V的异常读数；不能作为曾验证TDO正常的证据。
- 正确接地后所见约3.1～3.3V及输入脉冲，不能转记为TDO输出。
- 未确认测点上的约200μs周期，不能用于断言“设置1kHz、实际5kHz”构成已确认故障。
- 二极管档TDO与TMS读数相近、TDO对地约200～300kΩ，只提供外围电气对照，不能证明绑定完整、内部输出正常或所有负载问题已排除。

### 3. 当前JTAG诊断结果

- 最小配置仅定义TAP，不创建CPU target、不执行halt，仍返回全零。因此上层CPU调试驱动及配置末尾halt不能解释最早的链路扫描失败。
- 请求扫描频率曾使用1000kHz、10kHz、1kHz，当前仍未得到正确ID及IR捕获值。
- 最新探针可被识别：序列号07000001002800114d0000094e523359a5a5a5a597969908，固件报告0254。旧成功记录的序列号不同，不能视为受控的两只探针对照。
- BYPASS请求IR=0x1F、输入A5A5A5A5与5A5A5A5A，十轮两组均读回00000000。脚本完成只证明命令执行，不证明目标已接受BYPASS。
- 仅有TAP的配置出现“gdb services need one or more targets defined”是配置未创建CPU target的预期提示，不能当作全零的根因。
- TDI→TDO直接调试器回环已准备，用户选择跳过，未执行；因此没有独立验证调试器接收通道正常。

### 4. 当前软件问题与限制

**直接mww的异常尚未最终解释。** 前期将时钟寄存器写成0x121仍读到0x101；UART控制寄存器及手工SBA实验也未获得一致的双图样写回读证据。这不能推导为“芯片整体不能写”：CPU邮箱写入与Flash写入校验已有独立历史成功结果。

**邮箱必须按具体版本解释。** 后期3248字节版本main未调用硬件控制器扫描/初始化，mailbox索引9未被该轮清零更新，0xFE不能当作MODULE_CTRL实时读回，更不能据此说I²C_EN=0。这不否定更早调用hw_bus_init版本的0x0F读回结果。时钟门控、模块使能、有效事务是三个不同验证层次。

**硬件I²C事务仍未通过。** 前期主要使用GPIO位操作扫描；部分版本只配置、读取控制器寄存器，没有发硬件事务。START、目标地址与FIFO组帧序列仍需结合实测确认。没有模块ACK/WHO_AM_I结果，不能汇报为I²C已跑通。

**UART配置和实际系统时钟尚未形成证据闭环。** “板上12MHz晶振，而波特率分频按16MHz计算”是待验证假设；未证明芯片当时实际使用12MHz主时钟。邮箱版无UART初始化/菜单时，本就不会输出banner，不能用这种版本直接复现旧串口故障。

**内部JTAG使能、复用与保护状态未读取。** 手册描述了关闭/恢复机制，但当前TAP未通，无法靠无效的寄存器读取判断状态。没有证据证明NVR关闭了JTAG；未烧入nCS新版的AF注释问题也不能直接解释当前故障。

**工具路径问题已经识别。** 旧OpenOCD解析Windows反斜杠路径可能去掉反斜杠，出现无法打开.i2c_diag.bin或日志落到错误文件名。给OpenOCD使用正斜杠路径或简单相对文件名。这与当前命令已完整执行却全零的现象不同。

## 三、接下来优先做什么

### 第一优先：在实际对应接点观察TDO，尚未完成

不再执行绿色5号→H7-13的跨编号电阻对照。先按实际插接关系认准H7-16连接的绿色载板接点，不把它直接称为“绿色8号”。

保留正常JTAG接线和供电，只用一个示波器探头：地夹接U5-10/GND，尖端接上述实际对应的载板TDO接点。通道DC耦合、探头与通道倍率一致、1V/div，自动触发并运行。用现有BYPASS脚本重复扫描，记录是否出现高低跳变；本步骤不烧录、不写寄存器。

- 同条件下若载板接点有跳变而U5-2没有，检查两点间的传输路径及实际接点。
- 若载板接点也无跳变，只能说明该处没有观察到目标返回；TAP状态、实际输入时序、内部供电/复位/复用、封胶内连接和输出驱动仍有待区分。
- TCK/TMS/TDI由DAPLink驱动，TDO由目标芯片驱动。输入有脉冲不能单独证明目标芯片已接受扫描，BYPASS命令完成也不能证明指令已被目标接受。
### 第二优先：恢复JTAG后核实软件状态

1. 读到历史正确ID 0x1e200a6f、IR捕获正常，再确认hart。
2. 备份并核对当前Flash镜像，确认实际运行版本。
3. 按真实版本解释新一轮邮箱，验证时钟门控、模块使能与相关GPIO配置。
4. 核对MPU模式、供电和波形，先取得GPIO探测ACK并读取WHO_AM_I，再验证硬件I²C事务。
5. 单独用已知发送图样验证UART TX、实际波特率和CH340跨设备接收。

## 四、汇报用结论

目前历史软件执行与邮箱诊断已有成功证据，但当前JTAG返回链路失效。底板JTAG线路导通、输入活动及外部复位电平已检查；U5-2及H7-16未观察到TDO返回跳变。旧绿色焊点OL的对应关系未核实，已撤回断路推论，尚不能判定芯片损坏。软件侧已核对历史烧录与诊断版本，时钟门控曾成功打开，硬件I²C事务和UART跨设备通信仍未通过。后续先在实际对应的载板接点观察TDO并定位返回异常、恢复JTAG，再重新核实当前固件并推进I²C通信。
