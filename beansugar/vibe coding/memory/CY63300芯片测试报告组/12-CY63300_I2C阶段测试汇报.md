# CY63300 I²C 阶段测试汇报

**日期：** 2026-09-29  
**对象：** CY63300（TinyRISC-V）I²C 外设与 MPU-9250/6500/9255 模块  
**测试方式：** OpenOCD + CPU 执行的诊断固件 + SRAM mailbox；当前没有逻辑分析仪和万用表。

## 一、汇报结论

目前已证明 CY63300 能被 JTAG 识别，诊断固件能从 Flash 启动并执行，且 CPU 能把结果写入 SRAM mailbox 供 OpenOCD 读取。GPIO 模拟 I²C 对模块地址 `0x68` 和 `0x69` 的探测均未收到 ACK。

需要区分两个状态：系统级 I²C 时钟门控已经打开；但本轮诊断没有实际验证 I²C 模块使能位。源码定义了硬件初始化函数，但当前 `main()` 没有调用硬件控制器扫描流程。mailbox 索引 9 的 `0xFE` 没有在本轮清零或写入，属于旧值/残留的可能性很高，不能据此认定 `I2C_EN=0`。GPIO bit-bang 不依赖硬件控制器使能位。

当前不能据此判定 CY63300 的 I²C 控制器或 MPU 模块损坏。模块 XCS/nCS 的状态、实际供电和总线电气状态尚未被独立确认。

## 二、已经验证的事项

1. **CPU 执行与 mailbox 回读有效**
   - 诊断固件写入完成标志 `0x4D424F58`（ASCII `MBOX`）和完成状态 `0x0000600D`。
   - 固件写入的 SRAM 图样 `0xA5A55A5A`、`0x3C3C9696` 能从 mailbox 读回。
   - 这证明本轮固件代码执行到结束并完成 SRAM 写入；它不等价于验证 UART 输出。

2. **系统时钟门控状态**
   - `SYSCTRL_CLKEN` 地址为 `0x4002180C`。
   - mailbox 读到使能后的值 `0x00080021`，其中 bit 5（I²C 时钟门控）和 bit 0（GPIO 时钟门控）为 1。
   - 因此，I²C 外设时钟门控已打开。

3. **I²C 模块自身使能状态尚未验证**
   - I²C `MODULE_CTRL` 地址为 `0x40002800`，bit 0 为 `I2C_EN`。源码中的 `hw_bus_init()` 会写入 `0x0D`（I²C 与 TX/RX FIFO 使能），但当前 `main()` 没有调用 `phase_hw_scan()`，所以这段初始化并未在本轮运行。
   - 当前固件只清理了 mailbox 的部分索引，没有写入索引 9；读到的 `0x000000FE` 可能是 SRAM 旧内容，不是本轮 `MODULE_CTRL` 读回证据。
   - 后续应由 CPU 固件写 `MODULE_CTRL`、执行内存屏障并立即读回写入一个已清零的 mailbox 槽位，验证 bit 0；不要用 halted 状态下 OpenOCD 的直接 `mww` 结果代替 CPU 执行验证。
4. **GPIO 模拟 I²C 探测**
   - 探测地址：`0x68`、`0x69`，覆盖 MPU 地址脚 AD0 的两种常见地址选择。
   - ACK 时钟拍上，固件记录 SDA 已切为输入/释放（DIR=0），并在 SCL 为高时采样；原始采样值为 `3`，按固件位定义表示 SCL、SDA 均为高。
   - 两个地址都报告 NACK，即采样时没有观察到从机把 SDA 拉低。
   - 内部上拉关闭和开启时，释放态采样都为高。由于没有万用表或逻辑分析仪，这不能证明外部上拉阻值、实际波形、模块供电或引脚映射正确。

## 三、当前问题与未确认项

- **硬件 I²C 控制器还没有完成有效事务验证。** 本轮固件没有执行 `hw_bus_init()`；mailbox 索引 9 的旧值不能用来判断 `I2C_EN`。此前 OpenOCD 对外设寄存器的直接写入也不能作为 CPU 侧控制器使能的证据。
- **MPU 模块 XCS/nCS 未确认。** MPU-9250 数据手册将 nCS 标为 SPI 片选；I²C 模式需要保证对应接口处于正确状态。若 XCS/nCS 悬空或为低，可能造成 I²C 无应答，但目前这只是待验证假设。
- **供电与物理总线状态未测量。** 释放后读高并不证明 MPU 有电、共地可靠、SCL 有有效边沿，或 SDA/SCL 确实连到模块对应引脚。
- **UART banner 仍未定位。** CPU 能执行并写 mailbox，不等于 UART 的时钟、波特率、引脚复用和连接已经验证成功。

## 四、板上相关接口记录

依据现有板级网络表：

- H4-8：`SCL`
- H4-9：`SDA`
- H4-10：`UART0_RX`
- H4-11：`UART0_TX`，并与 H13-1 同网
- H4-16：`VDD_IO`
- H4-17：`GND`

H4-11 目前是裸小针脚，直接连接不方便；而且 UART 与当前 GPIO bit-bang NACK 没有直接关系，因此暂不建议为 XCS/nCS 测试先焊接 H4-11。不要把电压尚未确认的 H4-16 当作 3.3 V 电源使用。

## 五、建议的下一步（按优先级）

1. **先查模块 XCS/nCS。** 查看模块背面、准确型号资料或原理图，确认该脚是否已上拉/固定到合适的 VDDIO。不要盲接 5 V 或电压不明的电源。若确认模块的逻辑电压兼容，再用可逆方式确保 XCS/nCS 为高。
2. **确保硬件控制器模块使能并读回。** 在 CPU 执行的诊断固件中保留现有 `MODULE_CTRL` 其他位、置 `I2C_EN` bit 0，再把寄存器值写入 mailbox。先验证使能读回，再尝试硬件控制器事务。
3. **重复现有低速 GPIO bit-bang 探测。** 继续探测 `0x68`、`0x69`，记录 ACK 拍的 DIR、SCL/SDA 样本及 mailbox 状态。若出现 ACK，再读 `WHO_AM_I`；若仍 NACK，转查供电、共地、模块身份和实际接线，不能仅凭 NACK 判坏。
4. **等 GPIO bit-bang 能获得 ACK 后，再集中排查硬件 I²C FIFO/状态机。** 这样可以把“从机/接线不响应”和“控制器配置问题”分开。
5. **串口 banner 独立排查。** 对照实际系统时钟、UART 分频、TX 引脚复用和 CH340 RX 接线；不要把 UART 输出失败与 I²C NACK 合并成同一个结论。

## 六、结论边界

本阶段的可靠结论是：**CPU 执行和 mailbox 可用；系统级 I²C 时钟门控为开；I²C 模块使能位尚未由本轮固件验证；GPIO 模拟探测两个 MPU 地址均为 NACK。**

尚无证据证明：硬件 I²C 控制器已正确使能并完成事务、MPU 模块已进入 I²C 模式、总线电气波形正确、或模块本身损坏。
