# CY63300 V160C 独立连续刷新实测

2026-11-11，Asia/Shanghai。V160 烧录和完整扇区独立读回通过。用户拔除 DAPLink 后以 Type-C 冷启动，报告 OLED “只有第一行的hello，第二行没有计数”。连续刷新验收未通过。

用户保持供电接回 DAPLink。两次 SRAM 邮箱读回相隔约 17 秒且逐字节一致，SHA256 均为 7640DDD10C0140B84003589EE50A51E1B653A2281CA5A40B9912EDBC65BA993E。

| 项目 | 值 |
|---|---|
| V160 magic / stage | 0x4D423160 / 0x16000005（计数刷新阶段） |
| 上一完整计数（固件内部） / 当前目标 | 007 / 008 |
| 已确认结束的帧 / FIFO 写入次数 | 38 / 584 |
| 停住的位置 | 帧索引 38，字节索引 2。按代码预期是 008 的页 2 光标命令第 3 字节（0x10） |
| 邮箱记录 FIFO / STA / RAW | 0x204 / 0x03 / 0x00，快照对应 TX_NUM=2 |
| DONE / RESULT | 0 / 0。DONE 未写入，RESULT=0 是初始值，不能记作成功 |

三次实物寄存器只读采样一致：GPIOC_AFR1=0x1B，MODULE_CTRL=0xF，MCTR=0，FIFO_STA=5（TX_NUM=0），I2C_STA=3，RAW=0。邮箱中的 TX_NUM=2 属于早先快照。后续硬件已排空，但当前仍处于帧中且未发 STOP，符合 MCTR.STOP=0 时的行为。两种采样均未观察到 NACK 标志。没有连接 STM32 抓包，因此无法判定数字帧的线上字节和 ACK，也无法从固件内部记录推断屏幕曾显示 007。

优先怀疑 CPU 连续送字节时，前一字节留下的 WORK|DATA=3 与旧的 FIFO 空状态使轮询提前通过。随后出现 TX_NUM=2，支持进一步核查这个时序假设。程序为何没有写入 DONE、第二行为何一直空白仍未确认。下一项建议是固定显示 000，使用静态页光标和字模，拉开送字节间隔，同时以 STM32 高阻采集首个数字的命令与数据帧。先验证实际页地址和字模载荷，再恢复连续计数。当前保持实物状态，未复位、重发或改写 Flash。
