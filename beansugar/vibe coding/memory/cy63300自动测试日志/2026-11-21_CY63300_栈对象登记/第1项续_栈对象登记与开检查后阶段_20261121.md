## 0. 一句话结论

样片上这份 436 B 镜像**没有登记任何对象**（反汇编里没有 WRPLM/LDBNB/WRTAG，PLM 窗口 0x7000_0000 直读全 0），所以「登记后判定」在样片上根本无从谈起；开启 `safety_check_en`（CSR 0x803 bit0）之后，**最后一个能确认的阶段是 F 段完成标记 0x2000F000=0x4D533141 已写入**，此后的 0x118 那笔 store 之后没有任何 CPU 自己写下的阶段标记，因此「挂住」和「进了异常但清不掉使能」两种情形目前分不开。参考 RTL 里登记链是通的，但判定逻辑有一拍错位：越界 store 可被放行、合法 store 可被误报，**不能拿它当样片行为的解释或保护有效的证据**。

## 2. 四行交付表

### 2.1 真实栈范围

- **样片实测**：`sp=0x2001FF00`（固件 `li sp,0x2001ff00`，邮箱 w1 由 CPU 自己写下），帧 `0x2001FEE0..0x2001FEFF`（32 B，邮箱 w2 + frame.bin 内容：+0/+4 是 A 段 0x11112222/0x33334444，+16/+20 是复制结果 0x13579BDF/0x2468ACE0，+28 是 ra=0xE0）。
- **上限**：DataRAM 128 KiB，0x2000_0000–0x2001_FFFF。sp 之上的 0x2001FF00–0x2001FFFF 未被固件使用。历史实测 0x2002_xxxx 以低 17 位回卷（写 0x20020000 后 0x20000000 读到同值）→ **越过顶上界不 fault，而是回卷到 RAM 底**。
- **下界**：构建命令是 `-nostdlib '-Wl,-Ttext=0,-e,_start,--no-relax'`，**没有链接脚本、没有 crt0、没有 .map**，栈下界不由任何启动代码定义，仅由一条 `li sp` 决定。
- 判定：**只有这 32 B 帧有实证**；「整段栈」的范围没有定义，也没有守卫。
- 证据：`snapshot_20261121_103951_readonly\snapshot.json`、`frame.bin`、`mbox.bin`；`stack_check_20261120\build_and_sim.ps1`（无链接脚本）；`stack_check_20261120\firmware.S:16`。

### 2.2 对象登记

- **样片：未登记，且没有可观测的登记状态。** 436 B 镜像的反汇编里，除 `csrw mtvec` 与 `csrw 0x803` 外没有任何自定义安全指令；JTAG 直读 PLM 窗口全 0。
- **参考 RTL：登记链存在且可用（全核仿真通过）。** 编码从 `rtl/core/defines.v` 取：WRPLM `7'b1111011`(0x7B)、LDBNB `7'b1101011`(0x6B)、WRTAG `7'b1011011`(0x5B)。实测指令字：WRPLM base=`0x01C3807B`、bound(bit30)=`0x41D3807B`；LDBNB base=`0x00038D6B`（rd=s10）、`0x40038D6B`；WRTAG=`0x001D0D5B`。
  配方（每个对象）：① WRPLM id,base；② WRPLM id,bound（bit30=1）；③ LDBNB 指针寄存器,id（base）；④ LDBNB 指针寄存器,id（bound）——bnbcache 的 alloc 复用 `entry_state==2'b01` 且 ptr_id 相同的条目，所以两条填满同一 entry，并把 `bnb_index[rd]` 指到它；⑤ WRTAG 指针寄存器,指针寄存器（bit20=1）打标签。
  **坑**：WRTAG 的 rs1 字段必须填被测指针寄存器本身（`rtl/core/tinyriscv.v:957` 的 `exec_index_addr_i(ie_inst_o[19:15])` 用它查 index 判 `ptr_valid`）。
- **参考 RTL 的限制**：`rtl/perips/plm.v` 是 4 字桩（`PLM_SIZE=32'h10`、`PLM_WORDS=4`）→ 只有 pointer id 0/1 可寻址，与 `defines.v` 的 1024 个不一致；mepc 在这类异常里从不写（恒 0）。
- 判定：样片登记状态 = **未登记**（证据充分：反汇编 + PLM 直读）；参考 RTL 登记链 = **可用但仅 2 个 id**。
- 证据：`stack_reg_20261121\firmware_reg_disasm.log`、`sim_reg.log`、`tb_stack_reg.sv`；样片侧 `snapshot_20261121_103951_readonly\flash.bin`。

### 2.3 开启检查后最后可确认的阶段

- **样片**：能确认的是「F 段完成标记已写入」——0x2000F000=0x4D533141、r0/r1=1/1。之后到 0x124 之间只有 0x118 一笔 `sw t1,8(sp)`，**没有任何 CPU 自己写下的阶段标记**能证明它是否执行了这一笔、以及是挂住还是进了异常。
- **参考 RTL 对同一 436 B 镜像**：0x118 的未登记 store 被 EX 级组合逻辑（`rtl/core/ex.v:188-205`：`reg1_tag != TagEnable → boundary_check_fail`）拦截，**不上总线**，直接跳 mtvec；handler 清使能后成功写入 mcause=5、mepc=0、0x4D533142，frame+8 保持注毒值。
- **两者不一致**：样片结果块里没有 handler 的这些写入值。可能①挂在那笔 store（无异常）；②进了异常但 handler 里的 `csrw 0x803,zero` 清不掉使能，handler 每一笔 store 再次异常 → 递归陷阱，永远写不进任何字节。
- 判定：**待确认**（hang vs 递归陷阱分不开）。
- 下一条最能区分原因的证据：v2b 镜像的三段标记链（见第 3 节）。
- 证据：`stack_check_20261120\sim_stack.log`（参考 RTL 跑 436 B 镜像的完整输出）；样片 `snapshot_20261121_103951_readonly\res.bin`。

### 2.4 合法访问对照

- **样片（safety 关闭）**：A 段栈内读写落地（0x11112222/0x33334444）；B 复制返回 0，0x13579BDF/0x2468ACE0 落地；C（count=3）返回 1、帧内容不变；D（0x40000001）返回 1；E r0=1、r1=1。三轮逐字一致，**本轮只读快照的邮箱与之逐字相同**。
- **样片（safety 打开）**：没有对照——因为没登记，任何 store 都按「未登记」处理，无法构造「合法」样本。
- **参考 RTL（登记后）**：合法访问可过（v1 的 r0=0x4D533152 落地；v3 T2 的 frame+8=0xDEAD0001）；但判定有缺陷：
  - `rtl/core/bnbcache.v:326-356` 的 `check_valid_o` 是寄存器输出，`index_addr_i` 接的是 **ID 级** `id_reg1_raddr_o`、`check_addr_i` 接的是 **EX 级**地址 → 判定与访问指令错开一拍，实际用**下一条指令的 rs1** 去索引对象。
  - 后果一：后继指令 rs1 无 BnB 条目时 `check_valid` 保持 True → **越界 store 放行并提交**（v3 T1：0x2001FF08 写入 0xCAFE1111；v4 T1 同；v4 T2：0x2001FF0C 也写入 0xCAFE3333）。
  - 后果二：后继指令 rs1 是另一个带标签指针时拿错对象比 → **合法 store 误报 mcause=5**（v3 T3：0x2001FEEC 已提交 0xCAFE2222 之后仍抛异常）。
  - 后果三：**判定失败也会先提交再抛异常**（v3 T3 / v4 T2 都在内存里留下了数据）。
- 判定：样片合法对照（关闭检查时）**成立**；参考 RTL 的登记后判定**不可信**，既不能证明保护有效，也不能解释样片现象。

## 3. 下一步：v2b 诊断镜像（480 B，**未烧录**，等确认）

**为什么必须换镜像**：要区分「挂住」和「递归陷阱」，必须有在 `safety_check_en=1` 之后仍能落下、并且能被 JTAG 读到的标记。样片上 PLM 直读为 0，WRPLM 通道不可观测；唯一可靠通道仍是普通 store，所以只能在镜像里加「成对开关 + 分段标记」。

**改动（相对 436 B 镜像）**：
1. G 段改为：`csrw 0x803,1` → `csrw 0x803,0` → 写 M1(`0x2000F110`)=`0x4D533144` → `csrw 0x803,1` → 测试 store `sw t1,8(sp)` → `csrw 0x803,0` → 写 M2(`0x2000F114`)=`0x4D533145` → 写 `0x2000F12C`=`0x4D533143` → 自旋。
2. 陷阱入口改为：`csrw 0x803,zero` → 写 M3(`0x2000F118`)=`0x4D533146` → csrr mcause/mepc → 写 8/12(s10) → `lw t3,8(sp)` 写 `0x2000F120` → 写 `0x2000F11C`=`0x4D533142` → 自旋。
3. A–F 段、邮箱 w0..w15 布局、`stack_copy`、`framer` 全部保持原样（邮箱 word 值应与旧镜像逐字相同，便于证明本轮确实重跑）。

**新旧差异摘要**：436 B → 480 B；新增 8 条指令（2 次 `csrw`、3 处标记、1 处 slot 读回），G 段与陷阱入口重排；A–F 与 w0..w15 完全不变；sha256 `8407D655B853EE62342E6921E2F7ACCEF679A03B3F022210B774B16B945653FE`。

**参考 RTL 上的预期值（已跑通，v2b）**：M1=`0x4D533144`、M2=0、M3=`0x4D533146`、0x2000F11C=`0x4D533142`、mcause=5、mepc=0、frame+8=注毒值（store 不上总线）。

**样片上的判读矩阵**：

| M1 | M2 | M3 | 结论 |
|---|---|---|---|
| 0x4D533144 | 0x4D533145 | 0 | 测试 store 静默通过、无异常（与参考 RTL 的 TCU 拦截不一致）→ 再看 frame+8：0x5555AAAA=真的写进去了 |
| 0x4D533144 | 0 | 0x4D533146 | 进入异常且 handler 能清使能 → 看 mcause 与 frame+8 判断是否「先提交后异常」 |
| 0x4D533144 | 0 | 0 | **挂在那笔 store**（无异常、无进展） |
| 0 | — | — | `csrw 0x803,1` 本身就让核停住（连成对开关都没跑完） |

**烧录流程（确认后执行）**：留现有 436 B 镜像的第 0 页哈希 → 擦 0x200 页 → 编程 480 B → 独立回读整扇区比对 → SRST 重启 → 同一会话内先读完成标记与三段标记、再读 frame 与结果块、全部落盘后 `shutdown`。任何一步不符即停并保留现场。

**回滚**：旧镜像 `stack_check_20261120\firmware.bin`（sha 4451…84CC）随时可烧回。
