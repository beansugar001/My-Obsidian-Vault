## 1. 零基础名词卡（30 秒扫一眼就够）

| 词 | 大白话 |
|---|---|
| **CY63300** | 要测的那颗芯片（一块小板子）。 |
| **ST-Link** | 插在电脑 USB 上、另一头插板子的小调试器。它能让电脑"偷看/改动"芯片内部。 |
| **JTAG / SWD** | ST-Link 跟芯片说话的方式，可以理解成"芯片的电话线"。 |
| **OpenOCD** | 电脑上真正去拨这根电话线的程序。你不需要手动开它，脚本会自己开。 |
| **固件** | 烧进芯片里、芯片一上电就执行的那段程序（`firmware.bin`，428 字节）。 |
| **Flash** | 芯片里"断电也不丢"的存储，固件住在里面，从地址 0 开始。 |
| **SRAM** | 芯片里"断电就丢"的内存，本测试的数据都在 `0x2000F000` 附近。 |
| **邮箱 / mailbox** | 约定的固定地址（`0x2000F000`），固件把结果一个字段一个字段写在这里，电脑再读走。 |
| **完成标记** | 邮箱第 0 个字。固件全部做完才写 `0x4D533132`；看到它就说明"这轮跑完了，可以读了"。 |
| **注毒（poison）** | 在让固件跑之前，先往内存里写一堆**互不相同的假值**（例如 `0xDEADBEEF`）。这样如果固件"本来该保持原样"，假值就该还在；假值被换掉，就说明它真的写过了。 |
| **前后快照** | 固件自己在下手之前读一遍目标、下手之后再读一遍，分别存进邮箱。前后一样 = 没被改。 |
| **返回码** | 固件函数返回的数字。复制成功返回 0；参数非法被拒绝返回 1。 |
| **RTL 仿真** | 不碰真板子，用芯片的设计代码在电脑里"模拟"跑一遍。它和实物是**两层证据**，可以互相对照，但不能互相代替。 |

## 6. 常见问题（都是本轮真踩过的）

### 6.1 报"已有调试进程在跑（openocd/gdb 等）"
说明有 OpenOCD、GDB、或别的调试软件没关。全部关掉再跑。脚本自己会**开一个、用完就关**，你不用手动开第二次。

### 6.2 报"连不上板子，看日志"
1. 看 ST-Link 的灯亮不亮；2. 拔插一次 USB；3. 打开它提示的 `openocd.log`，搜 `Error`。
最常见的两句：
- `Error: open failed` → USB/驱动问题；
- `Error: init mode failed / JTAG scan chain` → 接线松了或板子没供电。

### 6.3 报"板子里不是目标固件"
说明板上现在是别的固件（比如 LIVE 分支 512 字节那版）。两个选择：
- 想测 RAW 这版：`python 复测_整数溢出.py --reflash`（会先存一份现状快照，再擦第 0 页、烧 428 字节、再独立回读校验；全绿才继续）。
- 想先确认板上到底是哪版：打开 `runs\precheck_*\flash.bin`，或者看同目录 `mismatch.json`（它记了板上 sha256 和期望 sha256）。

> ⚠️ 重新烧固件属于"改板子状态"。按我们的规矩：**换镜像前先留旧镜像的哈希，换完独立回读校验**——`--reflash` 已经按这个规矩写好了，别绕过它手工烧。

### 6.4 报"这一步失败了，看日志"（下面跟着一个 openocd.log 路径）
先看那个 log 的最后 20 行。常见原因：
- 板子被别的程序抢走了（见 6.1）；
- 固件大小和模板不匹配（`01_固件\firmware.bin` 被换过而长度变了）；
- USB 接触不良。
**不要删日志**，那是证据。

### 6.5 我想用别的办法重启芯片（比如 `reset run`）—— 不要
这块板子的 `reset run` 是**坏的**，实测报：
`Hart 0 didn't run coming out of reset in 1s; dmstatus=0x430382`
本脚本用的是唯一可靠的替代：**halt → 把 PC 写成 0 → resume**（相当于让固件从第一条指令重跑）。
注意：PC 只能写成 0，写成别的值会报 `Written PC (0x…) does not match read back value (0x2c062df3)`——这是芯片的限制，不是脚本的 bug。

### 6.6 我想单步调试看它一步步执行 —— 也不要
本板单步（`step`）不可用，OpenOCD 返回 -4。所以这个包不提供单步功能，只看"跑完之后的邮箱"。

### 6.7 路径里有中文和空格，会不会出问题
不会。脚本里所有路径都加了引号、用大括号包住，中文和空格都测过了。**但你自己在命令行里敲路径时，记得加双引号。**

### 6.8 我想改测试条件（比如换一个长度）
先改 `01_固件\firmware.S` 里对应的地方 → 重新编译出 `firmware.bin` → 用 `--reflash` 烧进去 → 再跑。
**改完必须记录：哪个文件、改了什么、新固件的 sha256。** 换了固件却沿用旧结论，是最容易出的事故。

## 7. 这一项到底测了什么（为什么说这个测试"有说服力"）

被测的是一段"C 语言里的长度检查"逻辑：

```asm
li   t0, 2          ; 缓冲区一共 2 个字
bltu t0, a0, reject ; 如果请求长度 > 2，直接拒绝（先比大小，再移位，避免乘法回绕）
slli t0, a0, 2      ; 长度 × 4 = 字节数
...                 ; 真正复制
```

我们要验证的是：**当有人传一个巨大的长度（`0x40000001`，让它 ×4 之后溢出回绕成一个"看起来很小"的值）时，这段代码必须拒绝，而且一个字节都不能复制过去。**

### 7.1 我怎么确认"它真的没复制"，而不是"它复制了但我看不见"

关键在**注毒**这一步。开跑之前，脚本先往内存里塞一批**独一无二的假值**：

| 地址 | 塞进去的假值 | 这个格子本来该存什么 |
|---|---|---|
| `0x2000F038/03C` | `0xDEADBEEF` / `0xCAFEBABE` | 启动时的"原始目标值" |
| `0x2000F050/054` | `0x66666666` / `0x77777777` | 请求**前**快照 |
| `0x2000F058/05C` | `0x11112222` / `0x33334444` | 超长**后**快照 |
| `0x2000F060/064` | `0x88888888` / `0x99999999` | 溢出**后**快照 |
| `0x2000F01C` | `0xAAAAAAAA` | "溢出后内容保持"标志 |

跑完读回来：
- 那批假值**全被换成了真实结果**（`0x66666666` → `0x2468ACE0` 等），说明固件**真的**执行到了写这些格子的那几行；
- 而两个"快照"格子里写的是 `0x2468ACE0` / `0x13579BDF`——这是**被保护缓冲区里的真实内容**；
- 于是结论是：固件确实读了缓冲区、确实写了快照，**读到的内容和请求前一模一样**。这就排除了"固件根本没跑"和"读到的是上一次残留"两种误判。

（同一个道理也解释了历史上那个坑：如果不清零、不注毒，缓冲区里本来就躺着 `0x2468ACE0`，"保持原样"和"读到上次的残留"看起来完全一样，分不清。）

### 7.2 唯一没闭合的点：w7 = 0

固件最后会把"我判断内容有没有保持"写进邮箱第 7 个字（`0x2000F01C`）：

- 实物读回：`0`
- 同一份镜像在 RTL 仿真里：`1`

同一段代码、同一个镜像，一个说 1 一个说 0，这是**矛盾**。但它不改变主判据（返回码 1、快照一致、注毒覆盖证明都成立），所以我不把它算成"未通过"，也不并进"拒绝后读回像启动初值"那个历史现象，而是**单独列为待确认**。要不要继续查，等组会定。
